# 模型库左侧栏筛选功能补全：技术方案

## Context

模型库页面（`frontend/web/src/App.tsx` + `frontend/web/src/components/Sidebar.tsx`）左侧栏画了 18 个筛选分组，但排查发现：

- **只有两个真实接口**在为整个页面提供数据：`GET /v1/catalog`（免鉴权，`internal/app/catalog.go:69`）和 `GET /v1/models`（需 API Key，`internal/app/models.go:23`）。左侧栏本身**不发请求**——所有勾选/滑动都是改 `App.tsx` 内存里的 `filters`，再对已加载的 `baseModels` 做一次 `Array.filter`（`App.tsx:206-330`）。这是合理的架构（一次拉全量、前端做客户端过滤），不需要改。
- 但过滤所依赖的**字段**里，除了 `contextTokens`/`inputPricePerM`/`outputPricePerM`/`supportedParameters`（这几个确实来自 `GET /v1/catalog` 的真实字段）之外，其余全部要么是硬编码默认值、要么完全没接线：
  - `series`/`category`/`distillable`/`zeroDataRetention`/`inRegionRouting`/`modelAgeMonths`/`toolCallingCapability`/`hasDiscount`/`isDeprecated`：非 mock 模型时永远是固定默认值（`data/models.ts:719,735,738,740-746`），过滤逻辑本身是对的（`App.tsx:264-330`），但数据源是假的。
  - **Design Arena** 8 个滑块（`Sidebar.tsx:565-643`）：调用 `IndexRangeSlider` 时完全没传 `onChange`，滑动只改组件内部 `useState`，连本地过滤都没接通，`App.tsx` 里也没有对应的 filter 分支。
  - **Providers**/**Model authors** 候选项（`Sidebar.tsx:648-665`）：硬编码字符串数组，和后端真实厂商数据脱钩。
  - **收藏（Pin）**：`App.tsx:63,179-189` 的 `pinnedModelIds` 只是内存 `useState`，刷新即丢失；后端完全没有收藏相关的表/接口。
  - **Inactive models（Show deprecated）**：即使补上 `isDeprecated` 字段，`catalogHandler`（`internal/app/catalog.go:88`）目前对 `status != 'active'` 的模型直接 `continue`，deprecated 模型根本不会出现在 `/v1/catalog` 响应里，这个筛选项在数据源层面就被堵死了。

本方案按"能否独立交付、是否需要后端改动"分成 4 个阶段，阶段之间无强依赖，可以分别提交。

## 阶段 D：收藏（Pin）持久化

**现状**：`App.tsx:63` 初始值硬编码 `['deepseek/deepseek-pro']`，`handleTogglePin`（`App.tsx:179-189`）只改内存 `useState`，刷新即丢失；后端 `/console/*`、`/v1/*` 均无收藏相关路由（`internal/app/gateway.go` 全量路由见 66-131 行）。

收藏是"登录用户的账户级偏好"，和现有 `/console/api-keys` 一样按 `account_id` 隔离，复用 `console.RequireSession` 鉴权（`internal/console/middleware.go:22`），不走 `/v1` 的 API Key 鉴权。未登录访客走 `localStorage` 本地兜底（不需要后端）。

### D1. 数据库迁移

新建 `migrations/00016_model_favorites.sql`：


### D2. 后端接口

参照 `internal/console/handlers.go:127-215`（`HandleListKeys`/`HandleCreateKey`/`HandleRevokeKey`）的既有写法：

- `GET /console/favorites` → `HandleListFavorites`：按 `sess.AccountID` 查 `model_favorites JOIN virtual_models`，返回 `{"data": ["deepseek/deepseek-pro", ...]}`（虚拟模型 name 数组，前端直接拿来对比 `model.id`，不需要额外映射）。
- `POST /console/favorites` → `HandleAddFavorite`：body `{"model": "deepseek/deepseek-pro"}`，按 name 查 `virtual_models.id`，找不到返回 404，`INSERT ... ON CONFLICT DO NOTHING`（重复收藏不报错）。
- `DELETE /console/favorites/{model}`（`model` 做 URL path 参数，chi 路由 `{model}` 需要处理其中的 `/`——用 `chi.URLParam` + `url.PathUnescape`，前端调用时对 model name 做 `encodeURIComponent`）→ `HandleRemoveFavorite`：`DELETE FROM model_favorites WHERE account_id=$1 AND virtual_model_id=(SELECT id FROM virtual_models WHERE name=$2)`。

三个方法挂在 `internal/console/service.go`，handler 放 `internal/console/handlers.go`，都走 `SessionFromContext`（和 `HandleListKeys` 一样的鉴权模式）。

路由挂载：`internal/app/gateway.go:113-125` 的 `authed`（`RequireSession`）分组里加：
```go
authed.Get("/favorites", d.Console.HandleListFavorites)
authed.Group(func(mutating chi.Router) {
    mutating.Use(console.CSRFGuard)
    mutating.Post("/favorites", d.Console.HandleAddFavorite)
    mutating.Delete("/favorites/{model}", d.Console.HandleRemoveFavorite)
})
```
（`POST /favorites` 和 `DELETE /favorites/{model}` 是写操作，必须过 `CSRFGuard`，和 `api-keys` 的分组方式完全一致。）

### D3. 前端

- `frontend/web/src/api/console.ts` 新增（风格参照 106-118 行的 `login`/`logout`）：

## 阶段 E：左侧栏 UI/交互设计问题（独立于接口缺失，纯前端修正）

以上 A~D 都是"数据源缺失"问题——过滤逻辑是对的，缺的是真实数据。以下是审阅现有实现（`Sidebar.tsx`/`App.tsx`）后发现的、和数据源无关的**交互/文案设计缺陷**，不需要等后端改动，可以随时单独修。

### E1. "筛选条件 (N)" 文案与实际含义不符

`Sidebar.tsx:308-310` 顶部显示 `筛选条件 <span>({totalFilteredCount})</span>`，但 `totalFilteredCount` 实际传入的是 `filteredModels.length`（`App.tsx:489,515`）——即"当前筛选结果命中的模型数"，不是"已启用的筛选条件数"。用户勾了 3 个厂商后看到"筛选条件 (127)"，容易误读成"127 条筛选规则生效"。

**修复**：文案改成"匹配模型 (N)"或"结果 (N)"。如果确实需要展示"已启用筛选数"，需要另算一个 `activeFilterCount`（逐字段对比 `filters` 与 `DEFAULT_FILTERS`），和结果数分开展示。

### E2. 滑块刻度标签位置与真实数值不成比例

`SliderControl`（`Sidebar.tsx:160-172`）的 `ticks` 用 `flex justify-between` 把文字标签**均匀**摆开，和 `min`/`max`/滑块实际数值完全脱钩。以 Context length 为例（`Sidebar.tsx:349-358`，`min=0, max=1000`，`ticks=['4K','64K','1M']`）：数值 64（对应"64K"）在 0-1000 刻度上只占 6.4% 的位置，但视觉上画在轨道正中间（50%），给用户"中点≈64K"的错误印象——实际中点(500)代表 500K。Prompt pricing（`max=15`，`$0.50` 只占 3.3%）、Output pricing（`max=60`，`$2` 只占 3.3%）同样问题。

**修复**：要么把 tick 按真实数值比例用绝对定位摆放（`left: ${(tickValue/max)*100}%`），要么去掉中间刻度文字只保留两端 min/max 标签，避免给出虚假的"中点提示"。

### E3. 线性刻度不适合跨数量级分布的数据

Context length（4K ~ 1M+）、Prompt/Output pricing（$0 ~ $10+/M）这类数据现实分布高度集中在低端（多数模型落在 4K–128K token、$0–$5/M），线性 slider 把最常用、最需要精细调节的区间压缩到轨道最左侧几像素内——拖动 1px 可能跨过几十 K token 或几美元，几乎没法精确选到 32K/128K、$1/$2 这类常见阈值。这也是 E2 里 tick 视觉错位的根本原因，建议两个一起改。

**修复**：改成对数刻度（滑块位置→真实值用指数映射，`onChange` 里再换算回真实值），tick 的视觉位置自然就和数值对齐了。

### E4. 多处 Info 图标是摆设，没有绑定任何提示内容

`SidebarSection` 本身支持 `hasInfo`/`infoText`，通过原生 `title` 属性渲染 tooltip（`Sidebar.tsx:63-67`），"In-region routing"（`Sidebar.tsx:434`）、"Tool calling"（`Sidebar.tsx:476`）用了这个机制。但 Artificial Analysis Indexes 三项（`Sidebar.tsx:510,526,542`）和 Design Arena 全部 8 项（`Sidebar.tsx:563,574,585,596,607,618,629,640`）里裸写的 `<Info className="w-3 h-3 text-gray-400" />` **既没有 `title`，也没有接 `hasInfo`/`infoText`**——鼠标悬浮/点击什么都不会发生。这 11 处图标给用户"能看说明"的预期，实际是死的。

**修复**：给这 11 处 Info 图标补上 `title="..."`（说明每个 Index/Design Arena 维度具体怎么算），或者直接去掉图标，避免"UI 承诺了却不兑现"。

### E5. 折叠长列表会隐藏已选中的隐藏项，且无任何提示

`CheckboxGroup`（`Sidebar.tsx:85-124`）默认只显示前 3 项，点"更多..."展开、点"收起"收回。如果用户先展开选中了第 5 项，再点"收起"，第 5 项从视图消失但选中状态和过滤效果都还在生效（`selectedItems` 数组不变）——用户会看到模型列表变少了，但折叠视图里找不到任何"还有 N 项在筛选中"的线索，容易困惑"为什么结果变少了却看不到是哪个筛选造成的"。

**修复**：折叠状态下如果 `selectedItems` 里有条目落在被隐藏的范围内，要么强制展开，要么在"更多..."按钮上加数量提示（如"更多...（2 项已选）"）。

### E6. 语义相同的布尔筛选项交互模式不统一

Discounted（`Sidebar.tsx:334-346`）、Zero data retention（`421-431`）、Inactive models（`489-499`）都用单个 checkbox，语义是"勾选=只看满足的，不勾=不筛选（不代表排除）"；语义同样是布尔字段的 Distillable（`403-418`）却用了三态 radio（any/yes/no），能明确表达"排除满足的"。同一批"是否类"字段一部分能表达三态、一部分只能表达两态，用户很难预期哪个字段支持"排除"语义。

**修复**：如果三态确实是 Distillable 独有的产品需求，就在其余几项旁补一句说明为什么不一样；否则统一成一种交互模式（推荐统一用三态，实现成本低且表达能力更强）。

### E7. 长候选列表没有搜索/过滤入口

Providers、Model authors（阶段 A2 改成动态派生后会随真实厂商数量增长）用的还是纯 `CheckboxGroup`，展开后是一列纯滚动 checkbox，没有内置搜索框。目前 11 个候选项还能接受，一旦目录增长到几十个厂商，找一个特定厂商就要一路滚动查找，没有任何加速手段。

**修复**：给 `CheckboxGroup` 加一个可选的 `searchable` 模式（候选项超过某个阈值，比如 8 项，自动带一个小搜索框做前缀过滤），Providers/Authors 两处启用。

### E8. Design Arena 与 Artificial Analysis Indexes 视觉相同但量级/含义完全不同

Artificial Analysis 三项用 0-100 量级的百分位指数（`Sidebar.tsx:512-549`，`max=54/82/58`），Design Arena 八项用的是 Elo 风格原始分数（`Sidebar.tsx:565-643`，`max=1,387~2,000`）。两组用完全一样的 `IndexRangeSlider` 组件、完全一样的位置结构，用户很容易把两组数值当成同一套量级来比较（比如以为拖到"1,387"和拖到"54"是同样意义上的"满分"），实际是两套完全不同的评分体系。

**修复**：至少在两组标题下补一行小字说明量级差异（如"0–100 百分位" vs "Elo 原始分"），或者把 Design Arena 也归一化到 0-100，和上面一组保持视觉/心智模型一致。

以上 E1~E8 均为纯前端改动（文案/CSS/局部组件逻辑），不涉及接口或数据库，且相互独立，可以任意顺序、任意子集地单独提交。
