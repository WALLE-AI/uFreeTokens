# 基准测试与排行榜数据服务：现状分析与执行技术方案

## 0. 结论速览

- **后端目前没有任何"基准测试"或"排行榜"的接口、表或数据任务。** 前端 `BenchmarksPage.tsx`（1075 行）和 `RankingsPage.tsx`（1535 行）的全部数据都是组件内硬编码常量；`BenchmarksPage` 里展示给用户的 `curl https://api.ufreetokens.ai/v1/benchmarks` 示例指向一个不存在的接口。
- 后端**可复用的资产**有三块：
  1. `virtual_model_metadata.scores`（JSONB，运营录入，`GET /v1/catalog` 原样透传）——可以承载"单模型综合评分"，但键名没有约定、后端不校验。
  2. `request_logs` + `usage_hourly` 汇总表 + worker 汇总任务——排行榜里"按模型/厂商的 Token 用量、趋势、延迟"可以直接从这里派生，但目前只有运营后台 `GET /stats/usage`（需管理员权限）能读。
  3. `GET /v1/catalog` 的价格、上下文窗口——"性价比散点图""单次会话成本""上下文窗口"三个板块只需前端计算，无需新接口。
- 排行榜 14 个板块里，**6 个可以用现有数据在第一阶段落地**，**4 个需要先在请求链路上补采集字段**，**3 个（按任务分类、多语言、编程语言）当前没有合规可行的数据来源，建议先隐藏**。
- 基准测试需要**新建数据模型**（基准定义、评测批次、评测结果）+ 运营录入/导入接口 + 公开只读接口；数据来源短期靠运营录入公开评测结果，长期可用自建评测（经由自家网关跑，成本/速度/错误率直接取自 `request_logs`）。

本方案分 5 个阶段（§5），阶段 0/1/2 互相独立、可并行，总计约 12～15 人日（不含可选的阶段 4）。

## 1. 现状分析

### 1.1 前端

| 页面 | 数据来源 | 问题 |
|---|---|---|
| `components/BenchmarksPage.tsx` | `benchmarksData: BenchmarkItem[]`（`:86` 起，11 个基准：T²-Bench Airline、Image、Video、Memes、Sketch、Games、GPQA Diamond、BrowseComp、DeepSearchQA、HLE、WideSearch），分 5 类 agents/media/artifacts/reasoning/search | 全部写死；`allModels` 入参实际未参与数据计算；`:899/:907` 的 API 示例接口不存在；订阅框默认值（`newsletterEmail` 的 `useState` 初始值）写死了一个具体的邮箱地址，所有访客都会看到，需要移除 |

### 1.2 后端已有资产

| 资产 | 位置 | 能力 | 限制 |
|---|---|---|---|
| 模型展示元数据 | `migrations/00014_virtual_model_metadata.sql`，`internal/catalog/catalog.go:37-47` | `scores JSONB` 随 `GET /v1/catalog` 公开 | 键名"由运营和前端约定，后端不解析、不校验"；前端 `data/models.ts:682 normalizeScores` 只读 `intelligenceIndex/codingIndex/agenticIndex` 三个 camelCase 键，`designArena` 完全未接线 |
| 元数据写入 | `PUT /virtual-models/{id}/metadata`（`internal/app/admin_routes.go:84`，`PermCatalogWrite`） | 运营整体覆盖写 scores | 无键名/类型校验，无历史，无来源追溯 |
| 请求明细 | `request_logs`（按月分区） | `virtual_model`、`channel_id`、`is_stream`、`status`、`ttft_ms`、`latency_ms`、各类 token、`charged_amount`、`user_agent` | 无工具调用次数、无图片输入计数、无应用归因、无生成阶段耗时 |
| 小时汇总 | `usage_hourly`（`migrations/00021_usage_rollup.sql`），`internal/reqlog/rollup.go RollupUsage`，worker 每 5 分钟汇总 | 维度：bucket × account × api_key × virtual_model × channel × provider；指标：请求数、成功数、token、金额、延迟/TTFT 直方图 | 行数随账户×Key 线性增长，直接跨全平台扫 7～30 天会越来越慢；无吞吐（tok/s）所需的生成耗时总和 |
| 统计查询 | `internal/admin/stats.go`（`GET /stats/usage`，`group_by` = virtual_model/channel/provider/account，自动选 raw/rollup） | 聚合逻辑、分位数近似都已写好 | 只挂在运营后台、需管理员会话；没有"厂商（模型作者）"维度 |
| 周期任务框架 | `cmd/worker/main.go` 的 `jobRunner.run(name, interval, fn)`，执行记录写 `job_runs` | 新增数据任务的标准方式 | — |

### 1.3 缺口汇总

1. **没有基准测试的数据实体**（基准定义、评测批次、每个模型的结果、样例）。
2. **没有面向 C 端的公开聚合接口**：排行榜是公开页面，不能复用需要管理员权限的 `/stats/usage`；并且公开用量数据需要隐私保护（最小账户数阈值、剔除内部/评测账户）。
3. **请求链路少采集了 4 类信息**：工具调用、图片输入、应用归因（调用方是哪个 App）、生成阶段耗时（算 tok/s）。
4. **`scores` 没有约定**：同一个指标现在可能被运营写成 `intelligence_index`，前端却读 `intelligenceIndex`，结果静默显示 0。
5. **accounts 表没有"内部/测试账户"标记**：自测、压测、评测流量会污染公开榜单。

### 2.2 基准测试（`BenchmarksPage.tsx`）

| 内容 | 来源方案 | 阶段 |
|---|---|---|
| 基准列表（名称、分类、描述、参评模型数、最近运行时间） | 新表 `benchmarks` + `benchmark_runs`，运营后台维护 | 2 |
| 每个基准的排行榜（质量分、单次成本、耗时、错误率） | 新表 `benchmark_results`；短期运营录入/批量导入公开评测结果，长期由自建评测生成 | 2（录入）/ 4（自建） |
| 质量 / 性价比 / 速度三项冠军 | 由 `benchmark_results` 在接口层计算，不单独存 | 2 |
| 样例媒体（图片/视频/Artifact） | `benchmark_results.extra` 里存对象存储 URL；首期可不做 | 2（可选） |
| 模型卡片上的综合指数（intelligence/coding/agentic、Design Arena） | 继续放在 `virtual_model_metadata.scores`，但加键名白名单与校验（§3.1）；远期可由 `benchmark_results` 加权自动生成 | 0 / 4 |

**数据来源的取舍**：

- **运营录入公开结果**（Artificial Analysis、LMArena、Design Arena、各基准官方榜）——上线最快，但要先确认各来源的**使用许可**，并在页面上标注来源与链接。
- **自建评测**——用平台自己的网关、以专用的"评测账户"跑开源基准（GPQA Diamond、HLE 等有公开题集的基准）。好处是成本、耗时、错误率可以直接从 `request_logs` 统计，数字和平台真实售价、真实线路一致；代价是需要评测 runner 和评分器，而且每轮评测都有 token 成本。可与 Harness 页面的 `ori eval` 规划合并。

## 3. 目标设计

### 3.1 scores 键名约定（阶段 0）

在后端固定一份白名单，`PUT /virtual-models/{id}/metadata` 写入时校验：只允许以下键，值必须是数字（`design_arena` 是一层嵌套对象），未知键返回 400。

```text
intelligence_index   coding_index   agentic_index
design_arena.{code, ui_component, game_dev, data_viz, three_d, image, video, svg}
```

- 后端：`internal/admin/catalog.go` 写入前校验；`internal/app/catalog.go` 输出不变（仍原样透传）。
- 前端：`data/models.ts normalizeScores` 同时接受 snake_case（正式）和 camelCase（过渡期兼容），并补上 `design_arena` → `designArena` 的映射。
- 数据修正：上线前跑一条 SQL，把已有 camelCase 键改写成 snake_case。

### 3.2 数据模型

新增迁移 `00024_benchmarks.sql`：

```sql
CREATE TABLE benchmarks (
    id               BIGSERIAL PRIMARY KEY,
    slug             TEXT NOT NULL UNIQUE,          -- gpqa-diamond，用于 URL /benchmarks/:slug
    name             TEXT NOT NULL,
    category         TEXT NOT NULL CHECK (category IN ('agents','media','artifacts','reasoning','search')),
    description      TEXT NOT NULL DEFAULT '',
    metric_name      TEXT NOT NULL,                 -- accuracy / elo / pass@1 ...
    metric_unit      TEXT NOT NULL DEFAULT 'percent',
    higher_is_better BOOLEAN NOT NULL DEFAULT true,
    source_name      TEXT,                          -- 外部来源名，自建评测为空
    source_url       TEXT,
    status           TEXT NOT NULL DEFAULT 'draft' CHECK (status IN ('draft','published','archived')),
    sort_order       INT NOT NULL DEFAULT 0,
    created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at       TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE benchmark_runs (
    id           BIGSERIAL PRIMARY KEY,
    benchmark_id BIGINT NOT NULL REFERENCES benchmarks(id) ON DELETE CASCADE,
    origin       TEXT NOT NULL CHECK (origin IN ('manual','import','self_eval')),
    run_at       TIMESTAMPTZ NOT NULL,
    notes        TEXT NOT NULL DEFAULT '',
    published    BOOLEAN NOT NULL DEFAULT false,    -- 同一基准只展示最新一次已发布的 run
    created_by   BIGINT,                            -- admin_users.id，审计用
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_benchmark_runs_latest ON benchmark_runs (benchmark_id, published, run_at DESC);

CREATE TABLE benchmark_results (
    run_id           BIGINT NOT NULL REFERENCES benchmark_runs(id) ON DELETE CASCADE,
    model_label      TEXT NOT NULL,                 -- 展示名；平台未上架的模型也能参评
    virtual_model_id BIGINT REFERENCES virtual_models(id) ON DELETE SET NULL, -- 已上架时关联，前端可跳 /models/<id>
    score            NUMERIC(10,4) NOT NULL,
    cost_per_task_micro BIGINT,                     -- 单题平均成本（微美元），自建评测由 request_logs 统计
    avg_duration_ms  INT,
    error_rate       NUMERIC(6,5),
    sample_count     INT,
    extra            JSONB,                         -- 样例媒体 URL 等
    PRIMARY KEY (run_id, model_label)
);
```

### 3.3 数据任务

在 `cmd/worker/main.go` 按现有 `jobs.run(...)` 模式注册：

| 任务名 | 周期 | 内容 |
|---|---|---|
| `public_usage_daily` | 30 分钟 | 从 `usage_hourly` 重算"今天 + 昨天"两天的 `public_model_usage_daily`（UPSERT，幂等），排除 `exclude_from_public_stats` 账户；首次部署时回填最近 90 天 |

### 3.4 公开接口（gateway，免鉴权，与 `/v1/catalog` 同级）

挂在 `internal/app/gateway.go` 的 `/v1` 分组、`auth.APIKey` 之外，加 `Cache-Control: public, max-age=300` 并在进程内缓存 5 分钟，按 IP 限流。

| 接口 | 说明 | 阶段 |
|---|---|---|
| `GET /v1/rankings/models?period=day\|week\|month&limit=20&series=none\|day` | 模型 token 用量排名 + 环比；`series=day` 时附带每日序列供趋势图 | 1 |
| `GET /v1/rankings/authors?period=` | 厂商 token 份额，Top 9 + "其他" | 1 |
| `GET /v1/rankings/speed?period=` | 输出 tok/s 的 P50，按模型 | 3 |
| `GET /v1/rankings/tools?period=` / `GET /v1/rankings/multimodal?period=` | 工具调用 / 图片输入请求量排名 | 3 |
| `GET /v1/rankings/apps?period=` | 应用 token 排名 | 3 |
| `GET /v1/benchmarks?category=` | 已发布基准列表，含三项冠军与参评数 | 2 |
| `GET /v1/benchmarks/{slug}` | 单个基准最新已发布 run 的完整排行榜 | 2 |

`/v1/benchmarks` 设计成**可选鉴权**：带 Key 与不带 Key 返回相同内容，这样页面上的 curl 示例不需要改成"必须登录"。

**公开口径与隐私规则**（同时写进"榜单统计方法与规则"文案）：

- 只统计成功请求的 input + output token。注意 `output_tokens` 取自上游 `completion_tokens`，**已经包含** reasoning token（见 `internal/adapter/openai.go` 的 `extractUsage`），不能再把 `reasoning_tokens` 加一遍。
- 某模型/应用在统计期内的独立账户数 < 3 时不上榜（避免从榜单反推单个客户的用量），归入"其他"。
- 标记了 `exclude_from_public_stats` 的账户（内部测试、压测、评测账户）不计入。
- **冷启动**：平台早期绝对量小，前端默认展示**份额与排名**，绝对 token 数可以通过配置项控制是否展示（`PUBLIC_RANKINGS_SHOW_ABSOLUTE`）。
- "最快推理速度"只展示模型维度，**不暴露上游渠道/供应商账户**（与 mock 里的 `fastestOn` 不同），属于商业信息，需产品确认后再决定是否展示 `provider_display`。

## 4. 关键实现要点

1. **复用 `internal/admin/stats.go` 的聚合代码**：公开接口不要直接调用它（它带账户维度、面向管理员），但分位数直方图的换算函数可以抽到公共包。
2. **作者推导规则只写一处**：Go 侧新增 `catalog.AuthorOf(virtualModel string) string`，物化任务和接口共用；前端保持现有的 `/` 前缀逻辑。
3. **`gen_ms` 的口径**：流式 = 最后一个 chunk 时间 − 首 token 时间；非流式无法区分排队与生成，**不参与**速度榜统计（在统计方法里说明）。
4. **应用归因字段做长度截断与规范化**（`app_name` ≤ 64 字符，`app_url` 只保留 scheme+host），防止被用来塞垃圾内容或个人信息。
5. **benchmark 结果与售价的一致性**：录入的外部结果里"成本"是外部来源口径；自建评测的成本取平台实际 `charged_amount`。接口返回 `origin` 字段，前端据此标注"外部数据 / 平台实测"。

## 8. 补充事项

以下几点不影响前面的阶段划分，但实现时必须一并处理。

### 8.1 数据口径

- **统计日的时区**：`public_model_usage_daily.day` 统一按 `Asia/Shanghai` 切日，接口响应里带上 `tz` 字段；否则"今日榜"在凌晨 0～8 点会和国内用户的直觉差一天。注意运营后台 `/stats/usage` 的 `tz` 参数缺省是 UTC（`internal/app/admin_stats.go:70`），做对账时要显式传 `tz=Asia/Shanghai`。`usage_hourly` 是整点分桶，UTC+8 没有半小时偏移，按东八区切日不损失精度。
- **模型改名与合并**：`usage_hourly.virtual_model` 是名称快照。虚拟模型改名后，新旧名称会在趋势图上断成两条线。物化时优先按 `virtual_model_id` 归并，展示名取当前 catalog 的名称；`virtual_model_id` 为空的历史行才回落到名称。
- **已下架/deprecated 模型**：历史期间内仍计入榜单（数据真实），但标注"已下架"并不可点击进入调用；不展示在"热门趋势"默认选中的系列里。
- **失败请求**：只统计 `status = success`；错误率单独作为指标，不影响 token 排名。
- **数据保留**：物化任务的回填上限受 `usage_hourly` 限制（首次部署回填 90 天，`cmd/worker/main.go` 的 `rollupBackfillDays`）；`public_*_daily` 本身体量很小，不设过期，长期保留用于年度趋势。

### 8.2 防刷与公正性

- **自刷流量**：厂商或用户可以自己刷量把某个模型推上榜。除"独立账户数 ≥ 3"之外，再对单账户贡献设上限——单个账户在某模型上的 token 计入量不超过该模型当期总量的 20%，超出部分不计入排名（原始数据不删）。
- **应用名冒用**：`X-Title` 是调用方自报的，任何人都可以冒用"Claude Code"之类的名字。上榜应用需满足同一 `app_url` 域名下 ≥ 3 个独立账户；运营后台提供应用名的屏蔽/合并列表。
- **评测流量隔离**：阶段 4 的自建评测账户创建时自动置 `exclude_from_public_stats = true`，避免评测本身推高被测模型的用量排名。

### 8.3 运维与可观测

- 物化任务沿用 `job_runs` 记录；超过 2 个周期未成功执行时告警（接入现有的 worker 告警规则）。
- 公开接口的缓存命中率、P95 耗时、限流拒绝数接入现有 observability 指标。
- 公开接口加一个总开关（配置项 `PUBLIC_RANKINGS_ENABLED`）；关闭时返回 503，前端展示"数据维护中"，便于出现口径问题时快速下线而不用回滚代码。

### 8.4 文档与对外说明

- 更新 `docs/API.md`（公开接口）、`docs/admin-api.md` 与 `docs/admin-openapi.json`（后台接口）。
- web 文档页（`DocsPage`）补充 `/v1/rankings/*`、`/v1/benchmarks` 的说明，以及 `HTTP-Referer` / `X-Title` 应用归因请求头的用法。
- 隐私政策需说明"平台会以匿名、聚合形式公开模型用量排名"，并提供账户级退出选项（即 `exclude_from_public_stats` 的用户侧开关，可放在个人中心 → 设置）。

### 8.5 SEO 与分享

排行榜和基准测试是站点最有搜索价值的公开页，但当前 web 是纯客户端渲染，爬虫拿不到数据。后续可选：构建时预渲染 `/rankings`、`/benchmarks`、`/benchmarks/:slug` 的静态 HTML（数据每天刷新一次即可），并为每页设置独立的 `<title>` 与 Open Graph 信息。不在本期范围内，列为阶段 4 候选。

### 8.6 页面上其余的假数据

`HarnessPage` 同样是全量写死的数据，`BenchmarksPage` 的订阅表单（`subscribed` 状态）没有后端接口，提交后只是前端提示成功。阶段 0 应把订阅表单隐藏或改为跳转外部表单，避免收集了邮箱却没有落库。
