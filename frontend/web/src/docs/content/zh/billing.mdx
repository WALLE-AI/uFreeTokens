## 计价货币与单位

所有模型都以**人民币（CNY）**计价。接口里涉及两种金额表示方式：

| 出现位置 | 表示方式 | 示例 |
|---|---|---|
| 目录售价 `sell_price.components[].unit_price` | 十进制字符串，单位：元 | `"1.5"` 表示 ¥1.5 |
| 余额、扣费等字段（字段名以 `_micro` 结尾） | `int64` 整数，单位：**微元** | `1500000` 表示 ¥1.5 |

换算关系：**1 元 = 1,000,000 微元**。显示给用户时除以 1,000,000 即可；在程序里请始终用整数微元做加减，避免浮点误差。

## 价格组成

每个模型的售价由若干**计量项**（meter）组成，在 `GET /v1/catalog` 的 `sell_price.components` 中列出：

| `meter` | 含义 |
|---|---|
| `input` | 输入 token |
| `output` | 输出 token |
| `input_cache_read` | 命中缓存的输入 token（仅部分模型单独定价） |
| `input_cache_write` | 写入缓存的输入 token（仅部分模型单独定价） |
| `output_reasoning` | 推理 token（仅当单独列出时才另行计价，否则计入 `output`） |
| `request` | 按次计费的项目 |

| `unit` | 含义 |
|---|---|
| `per_1m_tokens` | 每 100 万 token 的价格 |
| `per_request` | 每次请求的价格 |

价格表中没有列出的计量项不收费。

### 计算示例

以 `input` 为 ¥1.5 / 百万 token、`output` 为 ¥3 / 百万 token 的模型为例，一次输入 1,000 token、输出 500 token 的请求：

```text
输入：1,000 × 1.5 ÷ 1,000,000 = ¥0.0015
输出：  500 × 3   ÷ 1,000,000 = ¥0.0015
合计：¥0.003 = 3,000 微元
```

各计量项先相加，再对总额**向上取整到 1 微元**。如果平台对你的账户配置了折扣或免费额度等促销，实扣金额会在此基础上相应减少。

## 预扣与结算

每个计费请求都分两个阶段扣费：

<Steps>

<Step title="预扣（冻结）">

请求到达时，网关先按「最多可能花多少」估算一个金额并冻结：

- 输入 token：按请求体大小粗略估算（约每 4 字节 1 个 token）；
- 输出 token：取请求中的 `max_tokens` / `max_completion_tokens`、模型的最大输出、平台上限（当前为 8192）三者中的最小值。

如果**可用余额**不足以覆盖这笔金额，请求会直接返回 `402 insufficient_balance`，不会转发到上游，也不会产生任何费用。

</Step>

<Step title="结算">

上游返回后，网关按上游报告的**实际 token 用量**计算费用并扣款，同时解除这笔冻结。实扣金额与预扣金额无关，可能更低也可能更高。

如果上游在开始返回内容之前就失败了，冻结会全额释放，不收费。

</Step>

</Steps>

<Callout type="tip" title="余额较低时设置 max_tokens">

预扣金额与输出上限直接相关。余额不多时，在请求中设置一个合理的 `max_tokens`，可以降低预扣金额，避免因预扣不足被拒绝。

</Callout>

## 余额构成

账户余额分为三部分，可以通过 `GET /v1/usage` 查询（见[用量查询](/docs/zh/usage)）：

| 字段 | 含义 |
|---|---|
| `cash_balance_micro` | 现金余额 |
| `bonus_balance_micro` | 赠送余额，可能带有过期时间 |
| `frozen_micro` | 当前被进行中的请求预扣冻结的金额 |

```text
可用余额 = 现金余额 + 赠送余额 − 冻结金额
```

结算时**先扣赠送余额**（即将过期的优先），不足部分再扣现金余额。

目前网站暂未开放在线充值，新注册账户的余额为 0。

## 用量的来源：上游实测与估算

正常情况下，计费使用上游返回的真实用量。以下情况上游没有返回用量，网关会改用**估算值**计费：

| 场景 | 估算方式 |
|---|---|
| 流式请求中途断开（客户端关闭连接、上游中断） | 按已经转发给你的内容字节数估算输出 token（约每 4 字节 1 个 token），且不超过预扣时的输出上限；输入 token 沿用预扣时的估算 |
| 非流式请求，上游响应中没有 `usage` | 按预扣时的估算值（输入估算 + 输出上限）计费 |

流式请求中，你**不需要**自己传 `stream_options.include_usage`：网关总会向上游请求用量用于计费。只有你自己在请求里设置了 `stream_options.include_usage: true`，最后那个只含 `usage` 的数据块才会转发给你，详见[流式输出](/docs/zh/streaming)。

## 相关错误

| 状态码 | 错误码 | 说明 |
|---|---|---|
| 402 | `insufficient_balance` | 可用余额不足以覆盖预扣金额，请求未执行、未扣费 |
| 502 | `upstream_error` | 上游失败，预扣已释放，不扣费 |
| 503 | `no_available_channel` | 当前没有可用的上游渠道，预扣已释放，不扣费 |
